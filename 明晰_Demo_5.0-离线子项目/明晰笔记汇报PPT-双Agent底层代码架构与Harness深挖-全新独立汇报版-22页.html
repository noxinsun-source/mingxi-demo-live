11 / 22
最容易被误讲的一层

MCP 不是“让模型直接点 Canvas”。

宿主 Agent

  • Skill 规定：先 status/read，再生成计划。
  • MCP Tool 读取笔记、图和人工 operations。
  • 提交 dry-run 或 AgentPlan。
  • 发生 REVISION_CONFLICT 时必须重读、重规划。

本地 Canvas

  • 浏览器通过 /api/workspace 读取同一 JSON。
  • 拖动、改名、隐藏通过 /api/action 写回。
  • 写入同样携带 expectedWorkspaceRevision。
  • Workspace 更新后由 SSE 推送 revision。

两边不是互相遥控，而是同一个版本化状态容器的两个客户端。

功能 A 是 Turn-based 逻辑编排 Agent。模型读取筛选后的笔记、当前有向图、多轮对话和人工 Canvas 操作，只输出严格 AgentPlan；Harness 管理 Context、Provider、Structured Output、修复和 Patch 校验。模型不能直接改 Canvas，所有修改验证真实 ID 后才原子落图。Plugin 模式由宿主模型通过 Skill + MCP 操作版本化 JSON Workspace，Canvas 与 MCP 共享状态，并用 revision CAS 处理人机并发。

功能 B 是 Run-based 知识扩展 Agent。系统先用 MapSpec 约束粒度、跳数、节点与置信度，再让模型构造证据图，并通过 Frontier 状态机做 1–3 轮有界扩散。确定性编译器负责概念归一化、证据逐字校验、拓扑修复和五级投影，最后把输入、结果、Trace 和 Metrics 持久化为 D1 Run。所以核心是 Prompt + Context + Harness Engineering，而不是依赖某个现成 Agent 框架。
